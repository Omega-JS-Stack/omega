# Wave 5 Review Findings — desktop + extension + brands (2026-07-23)

## Context

This is an internal code-quality review of **Ian's own pre-release codebase**, commissioned by Ian and carried out on the repos he owns. It is wave 5 of the staged hardening pass over the OMEGA monorepo: each wave reads a package group, records defects, and ships one remediation checkpoint. No third-party system is involved and every item below is a defect in first-party code that the same effort then fixes.

The packages are unpublished (`private: true`, local `file:` specs, zero npm releases). Wave 4 (config + client + account + template-kit) shipped as cp266. This wave: `packages/desktop` (the Electron framework), `packages/extension` (the browser-extension framework), and the brand apps — `apps/sandbox-brand`, `apps/omega-playground`, `apps/newsflash-brand`, plus the sibling `../omega-brand` repo as read-only context. Reviewer A read desktop + extension; reviewer B read the brands.

Notable: reviewer B surfaced **uncommitted working-tree changes in `../omega-brand`** — the manage cycle (Ian's first `npm start` there) ran and wrote values back into `config/omega.json5`. Two of those writebacks are defects in the framework services that produced them (F9, F10); the omega-brand tree itself is Ian's to commit or amend.

All 15 findings were re-read in source by the coordinator before filing.

## Desktop + extension (reviewer A)

- **F1 (P2)** — Cold-start deep links dispatch via `setImmediate` in `deepLink.initialize()` (boot step 6), which fires during the `app.whenReady()` await — long before `omega.initialize` (main.js:423) boots Firebase in lib/client-bridge.js. The built-in `auth/token` route then hits the `!bridge._firebaseAuth` guard (client-bridge.js:244) and returns `firebase-not-loaded` — one warn, no retry, no queue. A user who completes the website sign-in while the app is closed (the OS cold-launches the app from the deep link) lands signed out with the one-hour token discarded. Warm-start and loopback paths work because the bridge is already up. `packages/desktop/src/lib/deep-link.js:78,89`. **Fix:** queue cold-start URLs and drain them after `manager.initialize()` completes instead of `setImmediate`.
- **F2 (P2)** — The consumer scaffold (`src/defaults/config/omega.json5:188`) and docs/auto-updater.md document an `autoUpdate.intervalMs` knob and a single-timer `_periodicTick` design; the code reads only `feedCheckIntervalMs` + `idleEvalIntervalMs` (DEFAULTS at auto-updater.js:77-85) — the single timer was deliberately reverted in 1.3.1 (header comment lines 74-76). A consumer setting `intervalMs` (the only documented name) changes nothing. **Fix:** update scaffold + docs to the real keys and the two-timer design (no alias — pre-release, no backwards compatibility).
- **F3 (P2)** — The 30-day pending-update gate is a startup no-op: `_reconcilePendingUpdate()` restores `downloadedAt`/`version` and calls `_enforceMaxAgeGate()` (auto-updater.js:520), whose `installNow()` returns false because `_state.code` is still `'idle'` (installNow guard at line 269 — only `'downloaded'` passes). The documented "force install at init" behavior never happens; the gate only takes effect after the next feed check re-downloads. `packages/desktop/src/lib/auto-updater.js:504-521,268-272`. **Fix:** when the gate trips at reconcile time, arm a force-install flag and trigger an immediate check; install on the `update-downloaded` event.
- **F4 (P3)** — `window.desktop.ipc.on()` (preload.js:32) returns `ipcRenderer.on`'s return value — useless across the contextBridge — and never tracks the wrapped handler, so listeners are unremovable. lib/ipc.js's header and docs/ipc.md:23 both promise an unsubscribe function, and every sibling subscription on the same surface (storage.onChange, theme.onChange, …) returns one. **Fix:** keep the wrapped handler and return `() => ipcRenderer.removeListener(channel, wrapped)`.
- **F5 (P3)** — `analytics.setUserId()` before boot stores the uid in `_pendingUid` "to apply at init" (analytics.js:207), but `initialize()` never reads it — the only other reference is the shutdown reset (line 314). The uid is silently discarded. **Fix:** apply and clear `_pendingUid` at the end of `initialize()`.
- **F6 (P3)** — `_maybeRehideDock()` derefs `manager.config.startup.mode` bare (window-manager.js:474); the `startup` section is optional (schema.js:416, required:false) and nothing seeds it. Every other reader guards (startup.js getMode uses `config.startup?.mode`). A config without a startup block throws a TypeError inside the hide handler on every macOS hide-on-close. **Fix:** route through `manager.startup.getMode()`.
- **F7 (P3)** — docs/managers.md ("manager.messenger — wired automatically"), CLAUDE.md, and the consumer scaffold (components destructure `messenger`) all present messenger as working, but every context (popup.js:31, options, sidepanel, page, content) assigns `this.messenger = null` and nothing constructs the `Messaging` class in lib/messaging.js — the export is dead code. Consumers following the docs crash on a null deref. messaging.js:10 also carries the degenerate check `if (!init || !init)` whose error message claims to validate `init.sender`. **Fix:** wire Messaging in each context's initialize (the docs' promise is the contract) and fix the init check.
- **F8 (P3)** — Two defects in lib/extension.js's chrome-API resolution loop: (1) line 96 assigns `self.api = browser.extension[api]` — a literal `.api` property instead of `self[api]`, so the browser.extension fallback never lands; (2) the `window[api]` probe (lines 81-85) runs AFTER the chrome probe and overwrites it — in any DOM context `window.history` exists, so `extension.history` becomes the page's DOM History object, shadowing `chrome.history` even with the permission held. **Fix:** correct the typo and remove the window probe (no chrome extension API lives on window) or demote it to a last-resort fallback.

## Brands (reviewer B)

- **F9 (P1)** — The authDomain contract collision. Firebase's OAuth handler (`/__/auth/handler`) is only served on `<projectId>.firebaseapp.com` — the 2026-07-19 live find recorded in the omega-brand config comment and AGENTS.md — so authDomain must be the firebaseapp.com value. But `@omega.js/client`'s `getApiUrl()` derives the production API base as `api.<authDomain>` (client index.js:628, with a legacy ITW-Universal-Auth comment), which would target the unresolvable `api.<projectId>.firebaseapp.com`. And the manage cycle's sdk-config ensure step writes `authDomain: domain` (the brand.url host) unconditionally (sdk-config.js:42) with a drift check that treats the deliberate firebaseapp.com value as drift — Ian's omega-brand `npm start` run demonstrably reverted the committed fix (uncommitted working-tree diff flips authDomain back to `omegajs.dev`). The playground's committed authDomain (`omegajs-playground.firebaseapp.com`, apps/omega-playground/config/omega.json5:101) is correct for OAuth but feeds the same broken API derivation. No single authDomain value satisfies both consumers. **Fix:** decouple the two — `getApiUrl()` derives from `brand.url`; sdk-config writes the Firebase-reported authDomain (`raw.authDomain`, the firebaseapp.com value). The next manage run then self-heals omega-brand's working tree in the sanctioned convergence path.
- **F10 (P2)** — The same omega-brand working tree gains `adsense: { accountId: "pub-7372939085773564" }` (ITW's shared AdSense pub id) directly above the committed comment "adsense: ABSENT — TABLED until omega publishes (Ian 2026-07-14)". The manage cycle's adsense service resolved the shared ITW account and wrote it into the production brand against the tabled ruling — the service reconciles whenever it can find any account, not only when the brand deliberately configures one. `../omega-brand/config/omega.json5` (uncommitted) + the manager's adsense ensure service. **Fix:** the service skips entirely (no resolution, no writeback) when the brand config has no `adsense` section; removing the written section from the omega-brand tree is Ian's call.
- **F11 (P3)** — The sandbox cross-stack e2e driver's catch block is empty ("step() already reported it") — true only for errors thrown inside `harness.step()`. Errors outside any step (`puppeteer.launch`, `browser.newPage`, `harness.preparePage`) are swallowed, `harness.failures` stays empty, and `harness.exit()` prints PASSED with exit 0 — a false-green on the gate HARD RULE 6 relies on. `apps/sandbox-brand/e2e/run.js:296`. **Fix:** record the caught error as a harness failure before teardown.
- **F12 (P3)** — `packages/manager/AGENTS.md` (line 1 of every brand's AGENTS.md chain) documents `npm run deploy` as the brand-root publish verb; omega-brand carries the script but apps/omega-playground, apps/newsflash-brand, and apps/sandbox-brand define only start/dev/pipeline — the documented verb fails with a missing-script error, and the brands are supposed to stay structurally mirrored. **Fix:** add the deploy script to all three in-repo brand roots.
- **F13 (P3)** — apps/sandbox-brand/README.md:23-25 documents `apps/backend/functions` and a five-level `file:../../../../../packages/backend` spec; the actual app has no functions/ directory and the dependency lives in apps/backend/package.json as the four-level `file:../../../../packages/backend`. The doc predates the src-pillar move. **Fix:** correct the bullet.
- **F14 (P3)** — Sandbox's `apps/backend/firebase.json` functions ignore list lacks the `deploy.log` entry present in the other three brand backends (playground, newsflash, omega-brand) — mirror drift; impact minimal for the offline sandbox but it signals the setup heal missed this file. **Fix:** add the entry; confirm the setup enforcement covers the functions ignore array.

## Amendment (2026-07-23, cp268 — F9 half reversed)

Ian's ruling reversed the **sdk-config half** of the F9 fix: authDomain is the BRAND host after all — a first-party authDomain is what keeps `signInWithRedirect` working under browser storage partitioning (the cookie concern UJM solved years ago), and the missing piece was never the value but the HOSTING: UJM's setup fetched Firebase's `/__/auth/*` helper files into the built site (`fetchFirebaseAuth`), and omega web had no equivalent — which is why the handler 404'd live on 2026-07-19 and why cp267 read firebaseapp.com as the only workable home. cp268 ports the mechanism (`packages/web/src/firebase-auth-helpers.js`, run by `omega build`; demo-* and projectless builds skip, fetch failures fail the build) and flips sdk-config back to writing the brand host. The **getApiUrl half stands unchanged** — the API base derives from `brand.url` on every surface precisely so authDomain stays free to be an auth-only concern, which this amendment exercised. The playground's committed authDomain moved to `playground.omegajs.dev`; Ian's omega-brand working-tree authDomain writeback (`omegajs.dev`) is now the correct value.
