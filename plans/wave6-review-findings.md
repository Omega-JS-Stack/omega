# Wave 6 Review Findings — DX + security (2026-07-23)

## Context

This is an internal code-quality review of **Ian's own pre-release codebase**, commissioned by Ian and carried out on the repos he owns. It is wave 6 — the last — of the staged hardening pass over the OMEGA monorepo: each wave reads a lens or package group, records defects, and ships one remediation checkpoint. No third-party system is involved and every item below is a defect in first-party code that the same effort then fixes. Packages are unpublished (`private: true`, local `file:` specs, zero npm releases).

Wave 5 shipped as cp267 (+ cp268 follow-through). This wave sweeps the whole monorepo through two lenses: **security** (reviewer A — first-party code posture plus the required triage of the 71 open dependabot alerts) and **developer experience** (reviewer B — CLI, scaffolds, docs parity, local-dev loop, plus the config-key inventory Ian requested for the de-branding decision). All findings were re-read in source by the coordinator before filing; one triage correction was made (esbuild, see S2 note).

## Security (reviewer A)

- **S1 (P2)** — The desktop remote-scripts and remote-config lanes execute network-fetched content with no transport check. `remote-scripts.js` resolves its URL from `config.remoteScripts.url` (free override, no schema) or `${brand.url}/data/scripts/main.js` (remote-scripts.js:47-52), fetches it as text, and `_execute()` runs it via `new AsyncFunction('manager','require', code)` with the live manager and real `require` — full main-process access (remote-scripts.js:120-127). `remote-config.js:82-87` derives its URL the same way. The `brand.url` schema rule permits `http://` (schema.js:56), so a cleartext-configured brand or an intercepted cleartext hop delivers unverified JavaScript into the main process. The signature-less emergency-hotfix design is intentional (EM parity); the cleartext transport path is the gap. **Fix:** refuse to fetch when the resolved URL is not `https:` (localhost/127.0.0.1 excepted for dev), log-and-disable otherwise, in both lanes. *Note:* this closes only the transport slice — the older Tier-3 question from plans/system-review-2026-07-20.md H1 (code-sign the payload, or ship the lane default-off) remains OPEN and Ian-gated; this fix does not answer it.
- **S2 (P2)** — Dependabot group: root `package-lock.json` (~55 alerts). Every alert is a transitive pin. The runtime-shipped vulnerable copies all descend from four unmaintained first-party dependencies: `mailchimp-api-v3` (backend) → request/tough-cookie/form-data/qs/uuid/tar; `npm-api` (backend + desktop + extension) → axios 0.21; `automately` (desktop) → cmake-js → request/tar; `chatsy` (client). The top-level axios/form-data/uuid are already patched — the alerts fire on the deep legacy copies, and `request` has no patched version. The rest are dev/build-only (electron-builder, node-gyp, jimp, serialize-javascript, diff, @opentelemetry/core). **Fix:** no dependency-bump pass clears these — replacing/removing the four legacy runtime deps is the move, as its own scoped checkpoint (Ian's go). *Coordinator correction:* the reviewer's "bump esbuild" item is already satisfied — `packages/web` declares `^0.28.1` and `npm ls` shows 0.28.1 everywhere; that alert is stale and should clear on the next lock regeneration.
- **S3 (P3)** — Dependabot group: `spikes/bakeoff-astro` (9 astro alerts). The spike is dead — not in the root `workspaces` array, marked `extraneous: true` in the lock. **Fix:** delete the spike (and siblings `bakeoff-eleventy`/`bakeoff-shared` if equally retired) and regenerate the lock — gated on Ian's confirm (deletion).
- **S4 (P2)** — Dependabot group: extension MCP server (hono ×5 + body-parser, alerts 50-54/70/71). All transitive via `@modelcontextprotocol/sdk ^1.29.0`, the server's only network dep; the server is a private offline dev tool. **Fix:** bump the SDK and regenerate its lock (mechanical, in cp269).
- **S5 (P3)** — Dependabot group: `packages/manager/extension` picomatch (dev-only, alerts 55-56) and the sandbox/playground backend function locks' uuid (alerts 1-2). **Fix:** picomatch updated (mechanical, in cp269). *Coordinator correction:* the uuid alerts are STALE — their manifests (`apps/*/apps/backend/functions/package-lock.json`) no longer exist on local HEAD; nothing to bump.
- **Coordinator discovery (triage-wide):** `origin/main` is 186 commits behind local HEAD (it sits at cp121c) — every dependabot alert was computed against that old tree. Alerts whose manifests were since deleted (the two brand `functions/` locks; likely others) resolve on the next push, which stays Ian-gated. The S2 chain analysis holds — it was traced against the LOCAL lock, where the four legacy runtime deps are still present.
- **Clean surfaces (traced, no finding):** the self-hosted `/__/auth/*` fetch lane, the desktop loopback auth flow (nonce-checked, 127.0.0.1-bound), the sanitize-url gate on `shell.openExternal`, the marketing/contact public route (reCAPTCHA + rate limit + anti-enumeration), the config secret-key validator, committed brand credentials (all demo/public-by-design), and the extension's `externally_connectable` entry (no external-message handler exists — the channel is inert).

## DX (reviewer B)

- **D1 (P2)** — `--help` is unimplemented everywhere and falls through to the DEFAULT command: on web it runs `setup` (scaffolds into cwd), at a brand root the manager runs `manage` (the full reconcile). web/manager disable yargs' built-ins (cli-run.js) so `--help` reaches the router with no positional and resolveCommand returns `defaultCommand` (cli-router.js:66). desktop/extension never disable the built-ins, so `--help` prints an empty yargs stub and `--version` prints `0.0.0` instead of reaching the alias-table version command. **Fix:** a shared help surface in the devkit cli-router (generated from the alias table + commands directory), `help`/`--help`/`-h` wired in every framework, yargs built-ins disabled on desktop/extension.
- **D2 (P2)** — Backend CLI: bare `omega` and any unknown command are a silent no-op — the flat `if (self.options.X)` chain (cli/index.js:64-186) has no else, so nothing matches, the function returns undefined, and the process exits 0 with zero output. **Fix:** bare invocation defaults to `setup` (mirroring every router framework); unmatched commands print the command list and exit 1.
- **D3 (P1)** — The contact form is dead on every new-world brand: the core page reads `omega.config.brand.contact['slapform-form-id']` (core/js/pages/contact/index.js:37) but nothing ever writes that key — the manager's slapform service writes top-level `slapform.formId`, and the Configuration blob (foot.html) never emits it. Every standing brand ships a contact page that reports itself unconfigured to Sentry on submit. **Fix rides the config rekey** (Ian's naming decision): the chosen neutral key gets emitted into the blob and read by the page, with a contract test. Fixing it earlier would hard-code a shape the rekey immediately replaces.
- **D4 (P2)** — The chatsy widget can never initialize on web: the client reads `config.chatsy.config.agentId` (client index.js:192) but chatsy only enters the blob via the `resolved.web_manager` loop (foot.html), which engine.js populates with firebase + payment ONLY — and the manager writes a different flat shape (`chatsy.agentId`). The same defunct loop leaves `pushNotifications` and the blob's `env:` line permanently null, and head.html's chatsy preconnect gate is permanently falsy. docs/config.md:379 still routes the legacy `web_manager` blob as a designed home. **Fix rides the config rekey** — one agreed shape shared by the manager writeback and the client reader, blob emission from the real home, the `web_manager` loop deleted.
- **D5 (P2)** — `cookieConsent`/`exitPopup`/`socialSharing` modules are unreachable: main.js:61-79 gates each on `omega.config[key]?.enabled`, but no schema declares the keys and the blob never emits them — and the skip log says "disabled in config", which no configuration can change. **Fix now:** truthful log ("not configured"). **Module fate** (give the keys a real home or remove the modules) is an Ian call at triage.
- **D6 (P3)** — Flag-alias drift across the mirrored CLIs: `-t` means translate on web but test on desktop/extension; `-d`/deploy aliases exist only on web (desktop/extension ship deploy.js reachable positionally but unaliased and undocumented); backend's clean is only reachable as `clean:npm`. **Fix:** `-t` = test everywhere (web translate keeps `--translate`/`translation`), deploy aliases added to desktop/extension, backend accepts bare `clean`.
- **D7 (P3)** — cli-router unknown-command errors are doubled ("Error executing… Error: Command… not found") and list no valid commands; the same catch prefixes every legitimate command failure with wrapper noise. **Fix:** unknown command prints the available-commands list and exits 1; real command errors surface once, unprefixed.
- **D8 (P3)** — CLI docs parity: extension docs/cli.md claims BXM-era aliases `xm`/`ext` (bins are omega/omg/mgr/omega-extension); extension + desktop AGENTS.md command tables omit shipped commands (deploy; desktop logs); extension README onboards via the legacy Ultimate Browser Extension template and links the monorepo at the old ITW org. **Fix:** correct all four surfaces.
- **D9 (P3)** — Config key inventory (the deliverable for Ian's de-branding decision — proposals only, table below). Vendor/brand-named keys remaining: `slapform`, `chatsy`, `replyify`, `gcp`, `firebase` (top-level, dual-homed projectId with `cloud.config`), `cloudflare`, `recaptcha`, `searchConsole`, `github`. None of the vendor service keys is declared in the config schema (schema.js), so typos validate clean and the de-facto config reference cannot describe them — schema declarations land in the same pass as the rekey.
