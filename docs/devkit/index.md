# @omega.js/devkit

Shared build-time internals for the OMEGA frameworks. **Private workspace package — never published to npm.** (The vendorable-private set is devkit, config, account, template-kit, analytics, monitoring — `VENDORABLE_PACKAGES` in [tools/vendor.js](../../packages/devkit/tools/vendor.js) is the SSOT.)

## How frameworks consume it

Frameworks require modules by name (`require('@omega.js/devkit/logger')`) and declare `@omega.js/devkit` as a **devDependency** (workspace-linked in the monorepo, absent from consumer installs). At prepare time, each framework's `preparePackage.hooks.after` runs [tools/vendor.js](../../packages/devkit/tools/vendor.js) (with `afterBlocking: true`, so a vendor failure aborts the prepare instead of warning past it), which copies the referenced modules into the framework's `dist/vendor/devkit/` and rewrites the requires to relative paths — so published tarballs are self-contained with zero **private** `@omega.js` references (enforced by CI's pack-smoke). Published `@omega.js` RUNTIME deps (desktop/extension's `@omega.js/client`) are never vendored — they stay normal package requires and resolve from the consumer install.

The closure covers the VENDORED trees too ([#739](https://github.com/Omega-JS-Stack/omega/issues/739)): a vendored module's own cross-package requires are rewritten to the sibling vendored copy (`dist/vendor/devkit/license.js` requires `../config/index.js` and `../account/index.js`), and any vendorable that only a vendored file needs is vendored beside it even when the host references it nowhere. Before that the copies shipped those specifiers verbatim, which resolved through the workspace symlinks in the monorepo and threw MODULE_NOT_FOUND on a published install, the private packages never being there. A published runtime dep stays a package require inside the vendored trees as well.

Vendored code resolves its deps (chalk, node-powertools) from the HOST framework's dependencies — the vendor tool fails if the host doesn't declare them.

## Test modules (`src/test/`)

Exported under the `./test/*` subpath, and the e2e LANES are the set that matters outside this package: the pieces below are what a brand's own browser lane and the monorepo's tier-2e lane both stand on, so there is ONE boot mechanism, not a copy per lane ([#775](https://github.com/Omega-JS-Stack/omega/issues/775)).

| Export | What it is |
|--------|-----------|
| `./test/boot-child` | `startChild({ bin, args, cwd, env, logFile, marker, timeout })` → `{ child, ready }` and `stopChild(child)`: the ONE way a lane boots a long-running child of the local stack (the emulator, `omega dev`) and stops it. `ready` resolves on the READY MARKER, matched against the BUFFERED output (a marker straddling two reads still counts) and resolving capture group 1, so a lane waits on what the child SAID rather than on a sleep or a listening port. Output is teed to `logFile` as it arrives, an early exit rejects with the code and the log path, and the stop is a process-GROUP SIGINT with a SIGKILL fallback, because firebase-tools and the dev server both spawn children a bare `child.kill()` would orphan. The local bin is spawned DIRECTLY, never through npx, whose Socket Firewall proxy env breaks firebase-tools' internal emulator calls |
| `./test/port-hold` | `holdClassicPorts()` → `{ servers, held, busy }`, `releasePorts(servers)`, `CLASSIC_HOLD_PORTS`: a lane OWNS a whole stack without disturbing a live dev boot by holding every classic port ([config.md](../shared/config.md)'s `CLASSIC_PORTS`, plus the two HTTPS proxy ports 4443/5443) for its run: the N7 allocator then bumps both children onto fresh numbers. Holding means all THREE addresses (127.0.0.1, ::1, wildcard), since SO_REUSEADDR lets a more-specific bind coexist with a wildcard one and anything less still reads as free. A port somebody else already owns is reported `busy` and left completely alone, partial binds closed |
| `./test/e2e-harness` | `new E2eHarness(brandRoot)` plus `discoverTargets`, `resolveLocalBin`, `resolveDevTarget`: a brand's whole LOCAL STACK, booted, and the step/log/teardown plumbing its lane authors steps against. `boot()` holds the classic ports, starts the backend emulator (`mgr emulator`, persona seeding included, ready on the post-seed marker) and the website's real `omega dev` on the allocated port both children hear as `OMEGA_WEBSITE_PORT`; `launchBrowser()`, `preparePage(page)` (console capture plus the resolved emulator map as the #300 FALLBACK), `step(name, fn)`, `teardown()` and `exit()` are the rest. Nothing static is built or served ([#775](https://github.com/Omega-JS-Stack/omega/issues/775)): `omega build` is always a PRODUCTION build, so a served build never connects to the emulator and a lane driving it proves a page nobody will load. A website target declaring no web framework has no dev server to boot and is refused by name, never dispatched to whatever CLI the climb finds |
| `./test/browser` | `launchBrowser({ from, args, ...launchOptions })`, plus `resolvePuppeteer(fromDir)` and `puppeteerRoot(fromDir)`: the lane's headless Chrome, resolved from the BRAND ROOT: the walk stops at the nearest package.json declaring `@omega.js/manager` (which carries puppeteer, so a brand installs nothing for its e2e lane), else at the NEAREST manifest above the caller, from which node's own resolution climbs to whatever install hoisted puppeteer (the outermost would skip a nearer copy a nested install deliberately put there). Launch args are the lane contract: `--no-sandbox` + `--disable-dev-shm-usage` are what make a CI container's Chrome start, `--ignore-certificate-errors` is what lets a page load the stack's mkcert origin. Resolution THROWS rather than degrading, so each lane decides for itself whether a missing browser is a skip or a failure |

`./test/e2e-harness` is the only module built on those three. `./test/journey-harness` is NOT: the outside-monorepo consumer lane keeps its own child spawn and ready-marker wait, and joining them is a later pass nothing depends on today. `./test/scope`, `./test/runner-core`, `./test/define-cases`, `./test/assert`, `./test/steps-log`, `./test/stdout-guard`, `./test/extended-mode-warning` and `./test/prompt-streams` are the rest of the exported set.

## Rules

- `src/` holds ONLY vendorable runtime modules — anything in `src/` ships inside every framework's dist. Build-side tooling goes in `tools/`.
- Tests: `npm test` (node:test). Migrates to the shared devkit test runner once that slice is extracted.
