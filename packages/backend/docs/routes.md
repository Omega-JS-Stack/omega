# Creating Routes, Events, Cron Jobs

Recipes for building consumer-side routes plus @omega.js/backend-side event handlers and cron jobs. See also [docs/schemas.md](schemas.md) for schema definitions, [docs/auth-hooks.md](auth-hooks.md) for auth lifecycle hooks, and [docs/common-operations.md](common-operations.md) for inside-the-handler patterns.

## New Route (Consumer Project)

Routes live at `src/routes/{path}/{method}.js` (staged to `dist/` by `omega build`: consumers are src-first, see [build-system.md](build-system.md)). The request pipeline loads the matching method file (`get.js` / `post.js` / `put.js` / `delete.js`), and falls back to `index.js` when no method-specific file exists.

A route exports an **async function receiving one object**, which the request pipeline builds (`src/omega/pipeline.js`):

```javascript
/**
 * POST /items - Create a new item
 */
module.exports = async ({ ctx, omega, user, data, usage, analytics }) => {
  if (!user.authenticated) {
    return ctx.respond('Authentication required', { code: 401 });
  }

  const firestore = omega.firebase.admin.firestore();

  // Count a use of a metered feature: check, count and write in ONE call
  await usage.consume('requests');

  // data strings are whitespace-trimmed by the pipeline; HTML is preserved.
  // Call omega.utilities.sanitize() at the HTML-insertion site, or opt the whole
  // route in to the pipeline's HTML strip with { sanitize: true }.
  const id = data.id; // generated by the schema (see schemas.md)

  await firestore.doc(`items/${id}`).set({ id, owner: user.uid, ...data });

  return ctx.respond({ id });
};
```

The argument's keys:

| Key | What it is |
|---|---|
| `ctx` | The request's `Context`: the logger, `respond()` / `redirect()` / `report()`, `ctx.request`, `ctx.req` / `ctx.res` |
| `omega` | The instance: `config`, `firebase.admin`, `utilities`, `email`, `ai`, `storage()`, the environment and URL helpers |
| `user` | The caller, a `User` from `@omega.js/account`, never null: `user.authenticated`, `user.uid`, `user.plan`, `user.roles.admin`, the stored fields |
| `data` | The input validated against the route's schema (see [schemas.md](schemas.md)) |
| `usage` | The counted-feature gate (see [usage-rate-limiting.md](usage-rate-limiting.md)) |
| `analytics` | Server-side GA4 events as the caller |

Every key is also on `ctx` (`ctx.user`, `ctx.data`, `ctx.usage`, `ctx.analytics`, `ctx.omega`); the argument is the convenience view. A route never constructs a service: it reads it off `ctx` or `omega`.

### CRUD method files

Every resource endpoint follows proper CRUD with **method-specific files** (plural-noun route names — `items`, not `item`):

| Method | File | Purpose | Path |
|--------|------|---------|------|
| GET | `get.js` | List all or fetch one | `/items` or `/items/{id}` |
| POST | `post.js` | Create new | `/items` |
| PUT | `put.js` | Update existing | `/items/{id}` |
| DELETE | `delete.js` | Delete existing | `/items/{id}` |

**GET routes exist for external API consumers.** The dashboard/frontend reads data directly from Firestore (faster, cheaper, no cold starts). POST/PUT/DELETE still go through Cloud Functions for server-side validation, usage tracking, and analytics.

**PUT and DELETE must verify ownership** before mutating:

```javascript
const existing = docSnap.data();

if (existing.owner !== user.uid) {
  return ctx.respond('Not authorized', { code: 403 });
}
```

Immutable fields (`id`, `owner`, `stats`, `metadata.created`) should NOT be editable via PUT. ID generation (POST) and ID-from-path extraction (GET/PUT/DELETE) happen in the **schema**, not the route — see [schemas.md](schemas.md).

### Key route patterns

- Short-circuit returns for auth/validation checks
- `data` contains the parsed and validated request input (from the schema)
- `ctx.respond()` for ALL responses (success and error)
- `admin.firestore().doc('collection/id')` shorthand for Firestore access ([firestore.md](firestore.md))
- Timestamps under `metadata.{created,updated}` ([firestore.md](firestore.md#document-metadata))

### The `test/` route folder is development-only

`routes/test/*` (the framework's own routes AND any a consumer adds under that folder) answers **404 in production**. The guard lives once, as the request pipeline's `guardDevOnly` step (`src/omega/pipeline.js`, `isDevOnlyRouteBlocked()`), the single place every request path converges (the deployed `omega_api` function, a consumer's own function through `omega.routes.run()`, and the custom server), so a NEW test route is gated the day it lands. Under the emulator (`isDevelopment()`/`isTesting()`) every one of them serves normally.

**Zero carve-outs.** The one route that used to need one — the liveness probe — is a real route now: see below.

Put debug/echo/reset routes in `test/` and they are safe by default. A route that must answer in production does NOT belong there.

Both the gate and the module loader read the route path **normalized** (`path.posix.normalize`, lowercased, `.js` dropped), because it arrives straight off the request URL: `./test/usage`, `.//test/usage` and `x/../test/usage` all resolve to the same handler and are all gated the same. A route path may also never escape the routes directory: a leading `..` or an absolute path is a flat 404, even when it climbs back in (`../routes/test/usage`). That is the pipeline's first step, `guardRoutePath` (`isRouteOutsideRoutesDir()`, same file).

### `GET /health` — the liveness probe

**`GET /omega/health`** (`src/omega/routes/health/get.js`) is the deployed backend's liveness and version endpoint. It is **public** (no auth) and **echoes no request input**: the payload is a fixed set of fields read from the instance, never from the request:

```json
{
  "status": "healthy",
  "timestamp": "2026-08-14T00:00:00.000Z",
  "environment": "production",
  "projectId": "your-project",
  "version": "1.4.0",
  "backendVersion": "5.9.0",
  "testExtendedMode": false
}
```

`omega manage`'s live API check reads it on a real host (`@omega.js/manager`'s testing service) and the test runner reads it to confirm the emulator's project and mode. `test/health` still serves the same handler in dev/testing for anything that has not moved yet, but it is a `test/` route — **404 in production** like the rest of the folder. Point liveness checks at `/omega/health`.

### Functions entry point (`src/index.js`)

The package's main export is the ONE instance; a consumer never writes `new`. `initialize()` is synchronous (Firebase reads the file's exports at module load) and returns the instance. `omega.functions` is the Cloud Functions map the framework filled (`omega_api`, the auth and Firestore triggers, the cron schedules); a function of your own joins it, and the map is the file's export:

```javascript
const omega = require('@omega.js/backend');

omega.initialize({
  identity: false,
});

/**
 * @route /items
 *
 * @method GET    /items            - List all items
 * @method GET    /items/:itemId    - Get single item
 * @method POST   /items            - Create a new item
 * @method PUT    /items/:itemId    - Update an item
 * @method DELETE /items/:itemId    - Delete an item
 */
omega.functions.items = omega.firebase.functions
  .runWith({ memory: '256MB', timeoutSeconds: 120 })
  .region(omega.project.resourceZone)
  .https.onRequest((req, res) => omega.routes.run('items', { req, res }));

module.exports = omega.functions;
```

`omega.firebase.functions` is the `firebase-functions/v1` SDK. `omega.routes.run(name, { req, res }, options)` runs the request through the same pipeline `omega_api` does, against the consumer's `routes/<name>/`. The schema defaults to the route name (`omega.routes.run('items', { req, res })` loads `src/schemas/items/`). The function's region must be `omega_api`'s, `omega.project.resourceZone`, because the hosting rewrite below reaches a function in that one region.

A consumer route is reachable ONLY through its own function and its own rewrite, at its own path (`/items`, never `/omega/items`): `omega_api` and `/omega/*` serve the framework's routes and the MCP endpoint, nothing else.

### The pipeline options

The third argument of `omega.routes.run()` tunes the pipeline for that function. Every key is optional:

| Option | Default | What it does |
|---|---|---|
| `authenticate` | `true` | Resolve the caller into `ctx.user` before the handler runs |
| `setupUsage` | `true` | Build `ctx.usage` for the request (it resolves the account only on its first `consume()` or `read()`) |
| `setupAnalytics` | `true` | Build `ctx.analytics` as the caller |
| `validate` | `true` | Validate the input against the route's schema into `data`. `false` hands the route the raw merged input |
| `includeUnknown` | `false` | Merge the validated input over the raw one, so keys the schema does not declare reach the route too |
| `sanitize` | `false` | Strip HTML from every string of `data`; a field declared `sanitize: false` keeps its HTML (see [sanitization.md](sanitization.md)) |
| `schema` | the route path | The schema name, when it differs from the route path |
| `parseMultipart` | `true` | Parse a `multipart/form-data` body (the `json` field whole, else the fields) |
| `routesDir` | `<cwd>/routes` | Where the route module is loaded from |
| `schemasDir` | `<cwd>/schemas` | Where the schema module is loaded from |

For operations that don't fit CRUD (e.g. `/items/:itemId/export`), add an **action sub-path** handled within the same Cloud Function (parsed from the request path) or as a separate function if resource needs differ significantly.

### firebase.json routing

Make routes public with rewrites. Use the bracket syntax so sub-paths like `/items/{id}` route correctly:

```json
{
  "hosting": {
    "rewrites": [
      { "source": "{/items,/items/**}", "function": "items" }
    ]
  }
}
```

**CRITICAL**: Without the `/**` wildcard, requests to `/items/{id}` won't reach the function.

**CRITICAL: Rewrite order matters — first match wins.** When multiple functions share a path prefix, the most specific routes MUST come first and the catch-all last, otherwise it swallows all sub-routes:

```json
{
  "hosting": {
    "rewrites": [
      { "source": "{/agents/*/chat,/agents/*/chat/**}", "function": "agentsChat" },
      { "source": "/agents/*/conversations/**", "function": "agentsConversations" },
      { "source": "{/agents,/agents/**}", "function": "agents" }
    ]
  }
}
```

Order: most specific → least specific → catch-all.

## New Event Handler

The framework's handlers live at `src/omega/events/{type}/{event}.js`: `auth/` (the Identity Platform user lifecycle), `firestore/{collection}/on-write.js` (document triggers), `cron/` (the scheduled runner, below).

A handler exports an **async function receiving one object**, like a route: `await handler({ ctx, omega, user, context, change, snapshot })` is the one call the event dispatcher makes (`src/omega/events.js`). A handler exported any other way is called as a plain function: its body never runs and nothing errors.

```javascript
/**
 * Notification subscription write handler
 */
module.exports = async ({ ctx, omega, change, context }) => {
  const firestore = omega.firebase.admin.firestore();

  ctx.log('Event triggered', context.params);

  // Event logic here
};
```

Which payload keys carry a value is the TRIGGER's business: auth events bring `user` (the Auth `UserRecord`) and `context`, Firestore document triggers bring `change` (or `snapshot`) and `context`; the rest arrive `undefined`. `ctx` (a fresh `Context` per event, with `ctx.request` null) and `omega` always ride. When `omega.handlers[<function name>]` is set, the dispatcher calls it as `hook(args, 'pre')` before the handler and `hook(args, 'post')` after it (the name is the running function's, `ctx.meta.name`).

The framework wires its own triggers in `src/omega/index.js`, each through the dispatcher:

```javascript
functions.omega_notificationsOnWrite = fn({memory: '256MB', timeoutSeconds: 60})
  .firestore.document('notifications/{token}')
  .onWrite((change, context) => event('firestore/notifications/on-write.js', { change, context }));
```

A **consumer project** wires its own trigger to `omega.events.run(name, payload)`, which runs the handler through the same dispatcher. The payload is whatever the trigger hands over (`{ user, context }`, `{ snapshot, context }`, `{ change, context }`):

```javascript
omega.functions.usersOnCreate = omega.firebase.functions
  .auth.user()
  .onCreate((user, context) => omega.events.run('users/on-create', { user, context }));
```

A relative name loads `${omega.cwd}/events/<name>.js`, the STAGED copy (`dist/events/`, the deployed functions source), so author it at `src/events/users/on-create.js` and let `omega build` stage it. A name starting with `/` is used verbatim, which is how the framework points at its own.

Throwing is the error contract: an `HttpsError` or an explicit numeric 4xx `code` rejects untouched (the trigger's client fault), and anything else is reported (logged AND captured to Sentry) as a server fault.

## New Cron Job (Consumer Project)

Create `src/hooks/cron/daily/{job}.js`. The runner reads the STAGED copy (`dist/hooks/cron/{name}/`, off `omega.cwd`), so author it in `src/` and let `omega build` stage it.

A job exports an **async function receiving one object**, like a route: `await handler({ ctx, omega, context })` is the one call the runner makes (`src/omega/cron.js`). Each job gets its own `Context`, and a job that throws is reported while the next one still runs. A job exported any other way is called as a plain function: its body never runs and nothing errors.

```javascript
/**
 * Daily job
 */
module.exports = async ({ ctx, omega, context }) => {
  ctx.log('Running daily job...');

  // Job logic here (Firebase Admin is omega.firebase.admin)
};
```

Every schedule works the same way (`daily/`, `frequent/`), and the framework's own jobs (`src/omega/events/cron/{name}/`) are written in this exact shape and run first.
